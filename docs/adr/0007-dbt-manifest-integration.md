# 0007. dbt integration through manifest.json v12 and meta.freshcal

## Status

Accepted.

## Date

2026-09-29.

## Context

dbt users already declare where their sources live and how to detect freshness
(`loaded_at_field`, `filter`). FreshCal should not require a second inventory of the
same tables. Two ways to read a dbt project exist: parse `sources.yml` ourselves
(needs Jinja rendering and project/reference resolution — effectively reimplementing
part of dbt), or read the `manifest.json` dbt writes, which contains the fully
resolved nodes. The manifest format is versioned; dbt 1.8–1.11 and "v2.0" declare
schema v12, and no v13 existed on 2026-09-28 (Appendix A). dbt ≥ 1.10 also offers
`loaded_at_query`, which we cannot execute without dbt's own query machinery.

## Decision

FreshCal reads `manifest.json` schema v12 only, from the path given by
`dbt.manifest`, and takes rules from each source table's `meta.freshcal` (or
`config.meta.freshcal`; both appear in the node's `meta`), verified with dbt-core
1.12.5 and dbt-duckdb 1.11.0 (BLUEPRINT.md §1.5 F6, §4.8). The mapping is fixed:
source ID from `source_name.name`, `relation` from `relation_name`, `loaded_at_field`
from `meta.freshcal` then the node's own field, `filter` from `meta.freshcal` then
`freshness.filter`. `name` and `relation` are rejected in `meta.freshcal` (E304) and a
node with only `loaded_at_query` is E303. Any other manifest schema version is E301 —
an explicit refusal, not a best-effort parse. The fixture manifest is regenerated by a
pinned script and committed, so tests never need dbt installed.

## Consequences

Rules live next to the sources they describe, and the same YAML file that works
standalone works in a dbt project. FreshCal is insulated from dbt's internals but
coupled to a file format: a dbt release that changes the schema version is a supported
failure with a clear message, and adding a version is a small, testable task. What we
cannot support in v0.1 (`loaded_at_query`, raw `sources.yml` parsing) is documented as
a non-goal rather than half-implemented. Three claims are kept apart in the docs:
format recognized (v12), tested (1.12.5), and declared by others but untested
(1.8–1.11, v2.0).

## Alternatives considered

- **Parse `sources.yml` with Jinja.** Rejected: requires a dbt-equivalent renderer, and
  "which value wins" would differ from what dbt itself computed.
- **Call the dbt CLI or dbt Cloud API.** Rejected: a subprocess or network dependency
  for data that is already on disk, and slow.
- **Read both v12 and v13 with a permissive parser.** Rejected: a silent mis-read of a
  changed format yields wrong verdicts; failing with E301 is the conservative
  behavior (ADR 0015's spirit).
- **Support `loaded_at_query` by executing the SQL.** Rejected for v0.1: it is dbt
  Jinja-plus-SQL whose meaning depends on dbt's adapter; E303 tells the user to
  provide `loaded_at_field` instead.
